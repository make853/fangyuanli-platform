> 文档版本：v1.0 Draft 1
> 视觉基线：当前 Flutter App
> 交互基线：iPhone 原型 v0.73
> 编制日期：2026-07-28
> 产品负责人：董事长
> 产品经理：Codex
> 文档用途：作为后续 Flutter App、服务端、数据库、地图、消息系统和测试工作的共同依据

## 0. 文档说明

### 0.1 决策状态

| 标记 | 含义 | 开发处理 |
|---|---|---|
| 已确认 | 已在讨论或原型测试中明确决定 | MVP 按本规格实现 |
| 暂定 | 当前采用，需在真实定位或灰度数据中调参 | 按当前值实现，同时保留后台配置能力 |
| 待确认 | 目前缺少足够依据，不能直接写死 | 开发前完成决策或采用安全默认值 |
| 后续版本 | 有价值，但不进入首个可运营 MVP | 预留扩展点，不在第一版实现 |

### 0.2 规格边界

本文件描述“方圆里”首个可运营 MVP 的产品行为，不等同于当前 HTML 原型。当前 Flutter App 是视觉基线，保留已经确认更清爽的图标、配色和页面质感；v0.73 是交互基线，保留已经反复验收的功能入口、操作反馈、页面跳转和返回路径。不得直接复制 HTML 原型代码。数据、权限、消息同步、定位、文件上传和审核必须由真实前后端实现。

### 0.3 版本目标

MVP v1.0 的目标不是一次完成所有社交平台能力，而是打通五条能真实闭环的主链路：

1. 用户登录并授权定位，稳定进入一个主广场和三个相邻广场。
2. 用户发现附近地点群，进入聊天；认证主体可以认领并管理地点群。
3. 用户创建、发现、报名和管理活动，并在活动群内交流。
4. 用户发布附近动态，完成浏览、点赞、评论、回复和通知跳转。
5. 用户申请好友、建立私聊、管理权限、拉黑和解除拉黑。

## 1. 产品定义

### 1.1 产品愿景

方圆里是一款以现实位置为入口的本地社交 App。用户无论到了哪里，都能快速发现当地正在发生的聊天、地点、活动和动态，在不暴露精准位置的前提下与附近的人建立联系。

### 1.2 核心价值

| 对象 | 核心价值 |
|---|---|
| 普通用户 | 到达陌生地点也能立即进入附近公共交流环境，认识人、找活动、看本地信息 |
| 居民 | 围绕小区和社区形成稳定但可治理的本地群 |
| 商家 | 拥有与真实地点绑定的长期社交入口，通过活跃度吸引附近用户 |
| 活动组织者 | 按位置、时间、人数和加入规则快速组建活动群 |
| 平台 | 用地理结构组织内容，避免依赖用户先建立大量固定群组 |

### 1.3 产品原则

- 位置用于匹配内容，不用于向其他用户展示精确坐标。
- 广场要稳定，不能因 GPS 漂移频繁切群。
- 地点是现实对象的数字入口，不要求用户必须走进地点边界才可看到。
- 私聊必须先成为好友，降低陌生人骚扰。
- 常用操作遵循微信等成熟社交产品的使用习惯，但界面保持方圆里的清爽风格。
- 所有按钮都必须产生明确结果、反馈或进入可操作页面，不保留“空按钮”。
- 返回必须遵循真实导航栈，用户从哪里进入就返回哪里。

## 2. 用户、身份与权限

### 2.1 基础账号

每个账号至少包含：用户 ID、方圆号、昵称、头像、个人签名、背景墙、性别、好友关系、黑名单、隐私设置和内容记录。

性别选项为“保密、男、女”。默认“保密”。其他用户能否看到性别由个人资料可见规则控制。

### 2.2 全局身份

| 身份 | 说明 |
|---|---|
| 普通用户 | 浏览、聊天、发布动态、创建活动、申请好友 |
| 好友 | 经双方好友流程建立的关系，可跨距离私聊 |
| 平台审核员 | 审核商家认证、地点纠错、举报和申诉 |
| 平台管理员 | 处理系统配置、违规、账号和紧急运营事项 |

### 2.3 群内身份

| 场景 | 身份 |
|---|---|
| 广场 | 当前可发言用户 |
| 商家地点群 | 群主、管理员、普通可见用户 |
| 小区地点群 | 居民、管理员、普通可见用户 |
| 活动群 | 群主、管理员、已报名成员、附近的人 |

群内权限必须由服务端判定，客户端只负责展示，不得仅依赖前端按钮隐藏。

## 3. 信息架构与公共导航

### 3.1 底部导航

底部固定五个主入口：

1. 广场
2. 地点
3. 活动
4. 好友
5. 我的

“我的”位于右下角，符合用户对主流 App 的习惯。动态放在“广场”内，不独立占用底部导航。

### 3.2 右上角发布入口

顶部“+”打开统一发布菜单：

- 发布动态
- 创建活动
- 扫码（加好友）

“我的”首页顶部同时保留搜索和“+”。

### 3.3 全局搜索

全局搜索从顶部放大镜进入，搜索结果按类别分组，不显示无意义说明文字。

| 类别 | 呈现方式 |
|---|---|
| 好友 | 头像、昵称或备注，点击进入资料或聊天 |
| 好友聊天记录 | 显示头像、发送者、时间和命中片段，点击定位原消息 |
| 广场聊天记录 | 明确标记“广场聊天记录”，点击定位原消息 |
| 地点 | 直接复用地点卡片，点击进入地点聊天 |
| 活动 | 直接复用活动卡片，详情按钮进详情，其余区域进聊天 |
| 系统消息 | 好友申请、活动通知、动态通知、发现期待活动 |

每类默认最多展示 3 条；超过 3 条时显示“查看更多好友”“查看更多地点”等对应入口。

搜索匹配采用规范化后的关键词或连续子串匹配。活动名“滨江夜跑·轻松5公里”必须能被“5公里”搜索到；没有关键词关联的好友不得因模糊算法误出现。不同类别分别建立索引，避免跨类别误匹配。

## 4. 地理与定位底层规则

### 4.1 坐标与地图

- 中国大陆地图、POI、逆地理编码和导航统一采用高德地图。
- 服务端内部保存用于计算的坐标；对其他用户不返回精确经纬度。
- 用户发布动态时可以选择是否显示地点名称，但不展示个人实时距离。
- 群、地点和活动可展示“离用户约多少公里”，该距离指固定地理对象，不是用户之间的距离。

### 4.2 定位授权

首次需要位置能力时申请系统定位权限，并解释用途。用户拒绝或关闭权限时：

- 不进入依赖实时位置的广场发言状态；
- 可查看历史进入、好友、私聊和自己的内容；
- 显示明确的开启权限引导；
- 不反复弹系统权限框。

### 4.3 广场区域

广场采用服务端权威的单层区域分区，每个区域对应一个稳定的广场 ID。区域不会跟随用户移动，也不会以每个用户为中心动态创建独立群。同一地图版本内，基础广场区域必须无重叠、无空缺，任意坐标只能归属一个广场。

首版区域由边长 2000 米的正方形网格生成，主广场加三个相邻广场组成约 4 公里乘 4 公里的四格区域。网格规则在全图逻辑上预先确定，方格记录、展示名和聊天空间在真实用户首次需要该区域时按需激活，不预建全部空方格。

正方形只是首版区域形态，不是业务表永久只能表达的边界。后续可以根据匿名聚合密度、道路河流、小区商圈和稳定生活区域发布新的不规则多边形边界版本。缩小区域产生的空缺必须在同一版本中分配给相邻区域；扩大区域占用的面积必须同时从相邻区域扣除。边界调整不得改变未拆分广场的 ID、会话和历史消息，也不得直接覆盖旧地图版本。

### 4.4 主广场与三个相邻广场

用户界面一次显示四个广场：

- 当前位置所属的主广场；
- 根据当前位置、网格边界距离和方向计算出的三个相邻广场。

四个广场都可以发言。用户切换广场时不显示精准位置，也不显示用户与其他人的距离。

当多个相邻广场距离相等时，使用确定性的排序规则，例如“当前锚点方向优先，其次稳定广场 ID”，不得在两次定位结果之间随机交换。

### 4.5 150 米锚点稳定机制

状态为“暂定”。用户第一次形成“主广场 + 三个相邻广场”组合时记录锚点。只要用户距离锚点不超过 150 米，即使 GPS 在网格边缘漂移，也维持原四广场组合。

超过 150 米后仍不立即切换，服务端结合以下条件重新计算：

- 定位精度达到可用标准；
- 连续多次定位指向新区域；
- 用户在新区域达到最短停留时间；
- 新组合与旧组合确有明显差异。

150 米、连续次数和停留时间均必须可配置。目标是稳定与省电，不是追求每秒更新。

### 4.6 广场命名

广场名由区域内部的稳定地标生成，与广场 ID 分离。外部地图搜索可以扩大范围用于发现候选，但最终入选地标必须具有可审计坐标，并被当前生效区域边界覆盖；格外地标评分再高也不得借给当前广场。位于共享边界上的地标使用与区域归属相同的确定性规则，只能分配给一个广场。

命名优先级暂定：

1. 短小、知名、稳定的公共地标或商圈名；
2. 公园、广场、场馆、学校等辨识度高的地点；
3. 简短路段或路口；
4. 社区名称；
5. 中性区域编号。

小区名称可能与地点群混淆，因此“社区/小区”命名优先级靠后。道路过长或缺乏区域辨识度时，不强制使用道路名。名称允许平台运营纠错，但广场 ID 不变。区域内没有合格地标时保留中性编号，不借用相邻区域名称，也不编造名称。

### 4.7 密度适配

“城市、郊区、乡镇”不靠行政名称硬判断，而根据一段时间内的匿名聚合数据综合判断：

- 单位面积活跃用户数；
- POI 数量和类型丰富度；
- 消息活跃度；
- 道路与建筑密度；
- 昼夜活跃波动。

MVP 第一版先使用统一正方形区域和统一邻接规则。后续区域调整以匿名聚合数据生成建议，经过重叠、空缺、用户迁移和聊天影响模拟后，按完整地图版本审核发布；不得根据短期人流实时改变边界，也不得在没有数据前过度复杂化底层。

## 5. 广场

### 5.1 页面结构

广场页顶部固定显示四个紧凑广场入口，不随聊天消息滚动离开屏幕。每个入口显示广场名和未读数量；选中的广场清晰但不占用过多内容高度。

广场内包含“聊天”和“动态”两个主内容区域。

### 5.2 广场聊天

- 当前四个广场均可进入并发言。
- 默认进入聊天底部，首先看到最新消息。
- 如果存在未读，屏幕内常驻“N 条新消息”入口；点击跳到第一条未读。
- 用户退出聊天后，该会话本次未读状态清零，对应红点和“N 条新消息”一起消失。
- 用户停留在历史位置时收到新消息，显示“↓N 条新消息”；点击回到最新。
- “有人 @ 我”“有人回复我”可作为独立跳转提示。
- 默认展示最近 7 天记录，继续上拉可加载更早内容，直到保存期限。

### 5.3 未读与导航红点

- 四个广场分别计算未读。
- 底部导航只统计红色未读，不统计免打扰的灰色未读。
- 双击底部导航红点时，按会话优先级定位下一条红色未读来源，不弹“已定位”提示，不增加红框。
- 进入并阅读该会话后，再次双击定位下一来源。

### 5.4 消息保留

广场文字消息服务端保存 1 年；图片、语音、视频保存 15 天。到期媒体应显示“内容已过期”，不得造成聊天结构错乱。

## 6. 地点

### 6.1 地点定义

地点是现实世界中可被识别的 POI 或区域，包括商铺、小区、娱乐、运动、场馆、公园、公共服务等。商家位于小区内部时，商家群和小区群仍是两个独立地点群，互不嵌套、互不从属。

### 6.2 懒创建

高德地图中的地点先作为候选 POI 存在。附近首次有用户打开 App 时，系统只为需要展示的 POI 建立或激活地点群；后续用户复用同一个地点 ID，不重复创建。

地点群没有普通用户创建者。系统生成后等待真实主体认领。

### 6.3 可见与进入

用户不必进入地点边界。只要地点落在用户当前发现范围内，用户即可看到地点卡片、进入聊天和按群规则发言。

地点卡片至少显示：名称、类别、距离、认证状态、热度等级和未读数。点击卡片任意非专属按钮位置直接进入聊天；聊天右上角“···”进入地点详情。

### 6.4 类别

MVP 地点类别至少包含：

- 餐饮与零售
- 小区与社区
- 娱乐与演出
- 酒吧与夜生活
- 健身房与运动场地
- 公园与景区
- 学校与公共服务
- 商场与商业街
- 交通与其他地点
- 历史进入

页面使用与方圆里视觉一致的自定义选择框，并支持地点关键词搜索。类别来自高德 POI 分类和平台映射规则，展示分类与底层原始分类分开保存。

### 6.5 自动分类与纠错

系统优先根据高德 POI 类型、名称关键词、建筑边界和平台规则自动分类。若分类错误：

- 商家通过营业执照认领后，审核员可同时纠正类别；
- 小区通过居民身份和投票流程提出纠错；
- 普通用户可提交地点信息反馈；
- 低风险纠错可以先进入人工审核队列，不要求用户完成复杂证明才允许反馈。

### 6.6 认证状态

前台统一显示“已认证”或“未认证”，不使用“已认领/未认领”。认证不等于活跃，也不自动提高热度。

未认证、连续 30 天无发言且无人管理的地点群自动隐藏。再次出现附近访问或有效内容时可恢复，不删除地点 ID 和必要审计记录。

### 6.7 五级热度

地点群热度分为：

1. 冷清
2. 中性
3. 活跃
4. 非常活跃
5. 火爆

热度依据近期独立发言人数、有效消息数、互动和时间衰减计算。历史累计消息不能让群永久保持火爆；无人发言时热度逐步下降。具体阈值为“暂定后台参数”，灰度测试后调整。

热度标签放在地点名称或“已认证”标签之后。列表默认综合距离和热度排序，用户可以自行切换距离、类别、热度和历史进入筛选。

### 6.8 商家认证

商家认证流程：

1. 申请人从地图或地点页选择目标地点群。
2. 上传营业执照、主体名称、统一社会信用代码、联系人、联系电话和必要的现场/门店证明。
3. 系统进行 OCR 与字段一致性校验，检测重复执照和重复认领。
4. 平台人工审核地点、主体和申请人关系。
5. 通过后申请人成为群主，地点显示“已认证”；不通过时返回明确原因并允许重新提交。
6. 营业执照只用于认证审核和合规存档，不向普通用户公开。

MVP 不承诺全自动认证。审核时效、企业实名方式和证件存储周期属于上线前待确认项。

### 6.9 商家群管理

| 能力 | 群主 | 管理员 | 普通用户 |
|---|---:|---:|---:|
| 发布/编辑公告 | 是 | 是 | 否 |
| 禁言和解除禁言 | 是 | 是 | 否 |
| 修改附近可见 | 是 | 是 | 否 |
| 修改发言规则 | 是 | 是 | 否 |
| 添加/移除管理员 | 是 | 否 | 否 |
| 修改认证主体 | 是 | 否 | 否 |
| 转移群主 | 是 | 否 | 否 |

群主添加管理员时可搜索自己的好友，并可从附近用户列表选择路人。正式服务端不得仅依赖“是否好友”限制授权，但必须有确认和审计记录。

禁言不要求填写原因。每次管理操作都必须返回成功/失败反馈并记录操作者、时间和变更前后值。

群主或管理员不受当前地理范围限制，可以从“我管理的地点”进入群组和查看仍在保存期内的记录。

### 6.10 小区管理员

小区初期不强制建立居民和管理员体系。当小区提出管理需求时：

- 最近 7 天内至少有 4 天在小区范围内出现，才具备本地活跃投票资格；
- 候选管理员由符合资格的居民发起；
- 票型为支持、反对、弃权；
- 到期未投票视为弃权，界面不显示“尚未投票”；
- 支持票必须多于反对票，且支持票不少于 5 票；
- 可以选出多名管理员；
- 同样规则可发起撤销管理员投票。

居民身份验证方案仍为待确认项。商家群不适用居民投票。

### 6.11 地点详情操作

地点详情右上角“···”至少支持：

- 分享地点
- 反馈地点信息
- 举报地点群

“其他”反馈或举报必须支持文本，并可上传图片或视频证据。只有该认证地点的群主或管理员能看到相应管理入口。

### 6.12 消息保留

地点群文字消息保存 1 年；图片、语音、视频保存 15 天。

## 7. 活动

### 7.1 活动发现

活动页支持按距离、类型、我的爱好、已参加和已结束筛选。活动卡片紧凑显示名称、开始时间、距离、人数、未读和状态。

“活动详情”按钮进入详情；点击卡片其他区域直接进入群聊。卡片不放导航按钮，活动详情页保留高德地图导航。

### 7.2 创建活动

创建表单包含：

- 活动名称
- 活动介绍
- 活动类型；选择“其他”时必须填写具体类型
- 地理位置；必须上传并可导航
- 开始时间
- 结束时间或“长期进行/无固定结束时间”
- 可见范围：500 米、1 公里、2 公里、5 公里、10 公里、30 公里
- 人数上限：自定义人数或不限人数
- 加入方式：直接加入或群主/管理员审批
- 发言规则
- 活动开始后的附近用户可见和发言规则

日期时间使用与 App 视觉一致的年月日时分选择器。选择“不限人数”时隐藏人数输入框。

### 7.3 人数与加入

- 自定义人数必须为正整数。
- 修改上限时不得低于当前已加入人数；例如已有 8 人，输入 7 时立即提示。
- 需要审批时，申请进入“好友 → 消息 → 活动通知”。
- 群主或管理员可在通知页直接同意或拒绝。
- 申请人头像可进入个人资料。
- 审批完成后状态保留，不立即从列表消失。

### 7.4 发言和可见规则

可选发言规则：

1. 附近的人都可以聊天
2. 只有已加入成员可以聊天
3. 只有群主和管理员可以发言

当加入方式为“需要审批”时，不展示与审批逻辑矛盾的“附近的人都可以聊天”选项。

活动可以设置“开始前附近的人可参与，开始后仅成员可参与”。群主还可随时关闭附近用户对群消息的查看权限。

### 7.5 活动角色与管理

群内只区分：群主、管理员、已报名成员、附近的人。

群主和管理员可：

- 发布和编辑置顶公告；
- 审批加入；
- 禁言或移除成员；
- 修改群可见与发言规则；
- 管理成员列表。

只有群主可修改活动结束时间、设置长期进行、转移群主和任命管理员。群聊设置中的选项必须与创建活动时使用同一套字段和枚举，避免前后冲突。

成员可以关闭自己设备上的公告展示，不影响其他成员。

### 7.6 活动结束

有结束时间的活动到期后进入“已结束活动”，但参与者仍可进入群聊和查看保存期内记录。长期活动不会自动结束，群主可随时补充结束时间。

已结束活动文字记录保存 1 个月，图片、语音、视频保存 3 天。起算点和进行中活动的保留策略在技术设计阶段统一定义，避免重复删除任务。

### 7.7 爱好与活动期待

用户可以选择爱好并输入期待关键词，例如“羽毛球”“游泳”“篮球”。系统匹配活动名称、类型、介绍和标签，同时校验活动距离和状态。

出现匹配活动时，由系统会话“发现期待活动”发送完整活动卡片。MVP 不再提供额外“提醒方式”选择。

## 8. 动态

### 8.1 动态入口与分发

附近动态位于“广场”内。发布后有两类可见用户：

1. 位于动态发布点所选范围内的用户；
2. 发布者允许查看动态的好友。

动态范围由发布者选择，最高 30 公里。发布者可选择是否显示地点名称。动态不向陌生人展示发布者精准坐标。

### 8.2 好友动态

“我的 → 好友动态”展示好友最新动态，按新到旧排列，下拉刷新。其点赞、评论、回复和详情能力与广场动态一致。

好友动态显示发布时间和可选地点，但不显示距离，也不显示“好友可见”文字。

### 8.3 发布

发布页以一个清晰的大“+”添加图片或视频，不重复显示冗余媒体说明。

- 图片自动压缩，在可接受清晰度下控制存储和流量；
- 视频最长 20 秒，最高 1080p；
- 超过 20 秒时明确提示并阻止发布；
- 同一张本地图片在同一次选择中只能选择一次；
- 移动端图片选择器显示勾选状态和顺序；
- 取消含内容的发布时询问是否保留草稿；
- 用户选择保留后，下次打开发布页自动恢复；
- “我的”中不单独设置草稿箱。

### 8.4 图片展示

单图完整显示原始长宽比并适当缩小，长图、宽图均不得裁掉主要内容。2 至 9 张图使用整齐正方形网格预览，点击任意图片进入可缩放大图浏览。

### 8.5 可见期限

发布者可设置动态可见期限：24 小时、7 天、30 天或永久。到期后不再进入附近流和普通资料浏览，但数据删除规则与用户主动删除分开处理。

动态正文和媒体默认长期保存，直到用户删除、账号注销或平台依规处理。

### 8.6 排序与筛选

- “最新”按时间从新到旧；
- “热门”不限制发布日期，以热度和内容质量排序；
- 距离筛选支持 1 至 30 公里；
- 日期筛选支持具体年月日；
- 选择某日后只展示该日内容，日内按新到旧；
- 下拉刷新可获得刚刚发布且满足范围的新动态。

### 8.7 编辑与删除

自己发布的动态在发布后 1 分钟内可编辑，超过 1 分钟只能删除。删除使用紧凑二次确认框。

### 8.8 互动与详情

- 动态显示配套的点赞和评论图标及数量；
- 点击动态进入独立详情页；
- 详情卡片宽度、头像和排版与动态列表一致；
- 评论按服务端顺序加载，支持评论点赞和回复；
- 点击底部评论入口直接聚焦输入框并评论主动态；
- 点击某条评论则在原详情页弹出键盘，回复该评论；
- 点击 @ 用户名或评论头像进入用户资料；
- 评论行为不得把页面错误切回广场动态列表。

### 8.9 动态通知

点赞、评论和回复进入“好友 → 消息 → 动态通知”。通知显示行为人、动作、摘要和目标动态；点击后直接进入对应动态详情并可定位相关评论。

### 8.10 举报

举报动态支持预设原因。选择“其他”时必须出现文本框，并支持图片或视频证据。

## 9. 好友与私聊

### 9.1 好友申请

陌生人不能直接私聊。用户必须先发送好友申请，并填写申请说明。

- 接收方可同意或拒绝；
- 未处理申请刷新后排在上方；
- 同意后显示“已同意”，不立即消失；
- 同意后双方进入好友关系和联系人列表；
- 系统不自动发送任何问候语。

### 9.2 私聊

好友私聊不受距离限制。文字消息保存 6 个月；图片、语音、视频保存 2 个月。

自己发送的消息不在气泡前显示“我”。双方头像都可进入对应个人资料。

### 9.3 好友设置

好友聊天右上角“···”与好友资料设置保持一致，包括：

- 查找聊天记录
- 置顶聊天
- 编辑备注
- 设置权限
- 删除好友
- 加入黑名单
- 投诉

备注是当前用户对好友的本地关系字段，不覆盖对方真实昵称。查找聊天记录显示头像、发送者、日期和命中片段，并能定位原消息。

置顶好友会话位于所有普通和系统会话上方，使用适度加深的背景颜色。取消置顶后恢复正常排序。

### 9.4 好友权限

权限为互斥选项：

- 允许查看我的动态信息、聊天
- 仅聊天

权限变更只影响对方查看当前用户内容，不应错误反向修改当前用户能看到的内容。

### 9.5 黑名单

好友和非好友使用同一黑名单机制，但系统保存拉黑前关系：

- 被拉黑者不能向当前用户成功发送消息，发送端显示失败；
- 拉黑立即出现在“账号与安全 → 黑名单”；
- 曾是好友的用户移出黑名单后恢复原好友关系；
- 原本不是好友的用户移出后仍是陌生人；
- 拉黑、解除和关系恢复必须双端一致。

### 9.6 投诉

投诉可选择原因、填写说明，并上传图片或视频证据。“其他”原因必须填写说明。

## 10. 个人资料与“我的”

### 10.1 他人资料

点击聊天、活动通知、评论、动态详情或地点群中的头像均进入同一套他人资料页。

未加好友时展示“添加好友”，不显示“暂不可私聊”等多余文案。已加好友时展示与好友关系对应的操作。

若用户禁止陌生人查看资料，陌生人只看到头像和个人签名；不展示历史动态、背景墙和其他受限信息。

### 10.2 自己资料

自己资料支持编辑头像、昵称、签名、背景墙、性别和隐私。资料中的动态必须完整显示文字、图片/视频、点赞数和评论数，点击进入动态详情。

### 10.3 “我的”首页

首页保持精简，包含：

- 个人资料和二维码
- 好友动态
- 我的活动
- 历史进入
- 消息通知与免打扰
- 账号与安全
- 帮助与反馈

不显示重复的动态/活动/收藏统计框，不设置收藏、我的爱好、图片视频与存储、草稿箱、认证与认领独立入口。

二维码位于箭头前并与箭头对齐，点击进入个人二维码页面。

### 10.4 历史进入

用户进入过的广场、地点和活动都记录在历史进入中。点击记录直接进入相应聊天，返回时回到历史进入页面，而不是跳到对应底部导航首页。

### 10.5 账号与安全

包含：

- 隐私
- 黑名单
- 退出账号
- 账号注销入口或说明

隐私中的“陌生人查看资料”“通过方圆号找到我”使用开关控件。

帮助与反馈第一版提供问题提交和联系入口；常见问题内容可在封闭测试产生真实问题后补充。

## 11. 统一聊天能力

### 11.1 输入栏

广场、地点、活动和好友私聊统一使用同一聊天输入组件：

- 左侧语音按钮
- 中间文本输入框
- 表情按钮
- “+”扩展按钮

语音模式显示“按住 说话”。组件行为和样式不得因聊天类型而分叉复制。

### 11.2 扩展面板

“+”包含：

- 相册
- 拍摄
- 位置

位置包含“发送位置”和“共享实时位置”。拍摄调用系统相机；语音调用系统麦克风。正式 App 首次申请权限，用户选择允许后不在每次操作时重复询问。

### 11.3 表情

- 提供完整基础表情；
- 支持自定义表情包；
- 长按别人发送的表情可保存；
- 我的表情采用紧凑整齐网格；
- 发送一个表情后面板保持打开，便于连续发送；
- 点击键盘或面板外区域时收起。

### 11.4 长按操作

长按文字消息显示：引用、转发、多选、删除。长按表情在此基础上增加“添加表情”。群聊中长按头像自动在输入框加入 @ 对方。

### 11.5 消息滚动

发送文字、语音、图片或表情后，刚发消息必须立即完整出现在可视区域底部，不要求用户手动下滑。

## 12. 通知、免打扰与未读

### 12.1 系统会话

好友消息页包含四类系统会话，并使用含义匹配的统一图标：

- 好友申请
- 活动通知
- 动态通知
- 发现期待活动

采用已选定的 A 套图标风格；动态通知为“信息框外轮廓 + 心形”。

### 12.2 全局免打扰

“我的 → 消息通知与免打扰”为直接开关：

- 开启后，广场、地点和活动默认免打扰；
- 好友私聊和好友页系统消息不受该全局开关影响；
- 免打扰会话仍在对应页面显示灰色未读点和数量；
- 不产生手机通知；
- 底部导航不统计灰色未读。

任意广场、地点或活动聊天设置中都可单独开启通知，覆盖全局免打扰。

### 12.3 红点与灰点

| 状态 | 会话列表 | 底部导航 | 手机通知 |
|---|---|---|---|
| 正常未读 | 红点和数量 | 计数 | 按系统权限通知 |
| 免打扰未读 | 灰点和数量 | 不计数 | 不通知 |
| 已读 | 不显示 | 不计数 | 不通知 |

未读状态必须存储在服务端，并在同一账号多设备间同步。

## 13. 数据保存与媒体规则

### 13.1 保存期限

| 数据场景 | 文字 | 图片/语音/视频 |
|---|---:|---:|
| 广场 | 1 年 | 15 天 |
| 地点群 | 1 年 | 15 天 |
| 进行中活动群 | 1 年 | 15 天 |
| 已结束活动群 | 1 个月 | 3 天 |
| 好友私聊 | 6 个月 | 2 个月 |
| 动态 | 长期保存 | 长期保存 |

所有期限应由后台配置。删除任务采用软删除、延迟物理清理和审计记录，防止误删和并发不一致。

### 13.2 媒体处理

- 所有视频最长 20 秒、最高 1080p；
- 图片按用途生成原图受控版、详情版和缩略图；
- 视频上传后转码为统一格式并生成封面；
- 上传失败支持重试和断点恢复；
- 文件上传完成后再发布消息引用，避免产生永久空消息；
- 到期媒体删除后保留消息类型和过期提示。

## 14. 状态流转

### 14.1 好友关系

陌生人 → 已申请 → 已同意/已拒绝。已同意后成为好友。好友可删除为陌生人，也可拉黑为黑名单；黑名单解除后根据拉黑前关系恢复好友或陌生人。

### 14.2 地点群

高德候选 POI → 懒创建地点群 → 未认证 → 认证审核中 → 已认证。未认证且 30 天无活动可隐藏；重新出现有效访问或内容后恢复。

### 14.3 活动

草稿 → 已发布未开始 → 进行中 → 已结束。设置长期进行时停留在进行中，直到群主设置结束时间或主动结束。

### 14.4 动态

草稿 → 已发布 → 1 分钟内可编辑 → 只可删除 → 到达可见期限后隐藏 → 用户删除或平台处置。

### 14.5 消息已读

新消息产生会话未读 → 根据免打扰成为红色或灰色 → 用户进入并完成阅读后更新最后已读消息 ID → 红点、灰点和“N 条新消息”同步消失。

## 15. 安全、隐私与治理

### 15.1 位置隐私

- 客户端只获取完成业务所需精度；
- 服务端位置数据按用途和时限保存；
- 不向用户开放其他人的坐标、轨迹或用户间距离；
- 位置日志与公开内容分离存储；
- 敏感位置接口必须鉴权、限频和记录审计。

### 15.2 最低治理能力

虽然早期不建设复杂 AI 审核，MVP 仍必须具备：

- 举报、投诉和证据上传；
- 黑名单；
- 群主/管理员禁言与移除；
- 平台人工审核后台；
- 违法和高风险内容的基础关键词、图片安全检测；
- 操作日志和申诉入口。

大规模 AI 自动判定、信用分和复杂风控属于后续版本。

### 15.3 权限和审计

所有群管理、认证、转移群主、隐私变更和删除操作均记录操作者、目标、时间、设备、变更前后值和结果。高风险操作需要二次确认。

## 16. 非功能要求

### 16.1 性能

- 首页首屏在正常 4G/5G 网络下目标 2 秒内可用；
- 聊天发送成功反馈目标 500 毫秒内出现；
- 列表使用分页和增量加载；
- 图片先显示缩略图，避免原图阻塞；
- 全局搜索首批结果目标 1 秒内返回。

### 16.2 稳定性

- 核心消息和关系数据不得只存在客户端；
- 服务端接口必须幂等，防止重复同意、重复发帖和重复消息；
- WebSocket 断线自动重连，重连后按消息序号补齐；
- 所有关键流程提供加载、空状态、网络失败和重试状态。

### 16.3 省电

- 前台按场景更新位置，不进行无必要秒级定位；
- 后台定位只在系统允许和业务必要时使用；
- 150 米锚点减少频繁地图和广场重算；
- 静止状态降低定位频率，明显移动后再提高。

### 16.4 可观测性

至少记录：登录成功率、定位授权率、广场切换次数、消息发送成功率、媒体上传成功率、活动报名转化、动态互动、好友申请转化、崩溃率和接口错误率。

## 17. MVP 范围与延期项

## 18. 上线验收标准

### 18.1 核心闭环

1. 两个真实账号在两台手机上可以完成好友申请、同意、私聊、拉黑、解除和关系恢复。
2. 两台手机处于相近位置时能看到一致广场 ID，移动和定位漂移不会频繁切群。
3. 四个广场均可发言，未读、免打扰、跳转和已读同步正确。
4. 地点群消息退出重进仍存在，认证后权限严格按角色生效。
5. 活动从创建、发现、申请、审批、聊天、管理到结束形成完整闭环。
6. 动态的图片、视频、评论、回复、资料页和通知都指向同一份真实数据。
7. 任意头像入口都进入正确资料；任意返回操作回到进入前页面。
8. 所有设置保存后有反馈、刷新后仍有效、另一台设备状态一致。

### 18.2 异常场景

- 无定位权限、弱网、断网、上传中断、重复点击和服务端超时均有明确反馈；
- 媒体过期、动态被删、用户被拉黑、活动已满等状态不出现死页面；
- 用户不能通过修改客户端请求绕过群主、管理员或隐私权限；
- 同一请求重复提交不会生成重复好友、重复活动成员或重复消息。

## 附录 B：原型与正式开发的关系

v0.73 已完成主要页面、按钮和单机交互验证，适合继续发现小的使用问题；它不具备真实多账号、服务端持久化、位置计算、实时消息和审核能力。

正式开发不得直接把单文件原型当生产代码迁移。应把它作为：

- UI 和交互参考；
- 已确认业务规则的演示；
- 测试用例来源；
- Flutter 组件和页面拆分依据。

本规格书是业务事实来源；若后续原型与规格冲突，以最新经确认的规格版本为准。
