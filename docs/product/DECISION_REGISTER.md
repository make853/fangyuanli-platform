# 方圆里产品决策登记册

> 作用：为产品、设计、Flutter、服务端、数据库、测试和运营提供唯一的决策入口。
> 本文件只登记结论与权威来源，不复制完整规格；具体行为仍以链接文件为准。

## 1. 权威顺序

发生冲突时，按以下顺序处理：

1. 用户最新明确确认并已写入本登记册的决定；
2. `docs/product/PRODUCT_SPEC.md`；
3. 已接受的架构决策记录（ADR）；
4. `docs/product/V073_INTERACTION_LEDGER.md`；
5. v0.73 原型和历史讨论记录。

原型负责说明经过验收的交互习惯，不是数据、权限或后端实现依据。历史构想不会自动覆盖正式规格。

## 2. 决策状态

| 状态 | 含义 | 开发规则 |
|---|---|---|
| 已确认 | 已确定且进入实现或验收 | 按权威来源实现，变更必须更新登记册和受影响测试 |
| 暂定 | 当前有安全默认值，仍需真实数据调参 | 参数必须可配置，不得散落硬编码 |
| 待确认 | 会改变产品或数据边界，现有证据不足 | 不擅自写死；到达最迟确认节点前必须决策 |
| 后续版本 | 已认可价值但不进入 MVP | 只保留必要扩展边界，不提前实现 |
| 已取代 | 被新决定替代 | 保留历史原因，但不得继续作为开发依据 |

## 4. 暂定与待确认决定

详细清单以 `PRODUCT_SPEC.md` 第 19 节为准。到达某项“最迟确认时间”时：

1. 产品负责人确认用户行为和商业取舍；
2. 技术负责人说明架构、数据迁移、合规、费用和回滚影响；
3. 结论写入本登记册并更新规格、契约、ADR和测试；
4. 没有结论时不得用页面常量或临时分支替代正式决定。

## 5. 变更流程

任何影响三个及以上场景、数据库身份、权限边界、消息语义或地理归属的修改，都按平台级变更处理：

1. 说明用户问题，不先指定代码解法；
2. 判断是场景特例还是公共规则；
3. 列出产品、架构、数据、兼容和风险影响；
4. 更新权威决定或新建 ADR；
5. 实现一次公共能力，由场景适配器接入；
6. 自动测试、A/B 测试和真机验收通过后建立 Git 检查点。

仅属于单一业务且不会改变公共语义的功能，可以在对应模块内实现，但仍不得绕过公共会话、关系、权限、媒体、缓存和导航边界。

## 6. 决策复盘节奏

- 每个业务纵切开始前：检查本模块待确认决定；
- 每个稳定版本合并前：检查本次是否产生新决定或取代旧决定；
- 每个阶段大会：复核 MVP 范围、风险、成本、真实用户数据和下一阶段；
- 上线前：逐项关闭会影响合规、费用、数据保留和商店审核的待确认决定。
