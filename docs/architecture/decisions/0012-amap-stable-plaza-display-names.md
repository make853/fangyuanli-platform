# 0012：高德稳定广场展示名

- 状态：已接受
- 日期：2026-08-02

## 背景

版本化网格已经可以稳定生成主广场和三个相邻广场，但中性的“区域广场 + 编号”只适合作为故障降级名称。用户需要一眼知道广场对应的现实区域，同时广场名称不能因网格边长、小商铺更名、道路过长或每次定位结果不同而反复变化。

广场的身份、会话、消息和锚点已经由稳定 `plaza_grid` ID 承载。地图名称只能是展示属性，不能重新定义广场边界或迁移聊天数据。

## 决策

1. `plaza_grids.id`、网格版本、坐标和 `conversation_id` 是稳定身份；高德只更新 `display_name` 与 `naming_source`，不改变广场、会话和消息归属。
2. 服务端使用高德 Web 服务逆地理编码，查询网格中心的 GCJ-02 坐标。不得把用户的实时位置、手机号或账号信息发送给高德。
3. 候选名称按稳定性排序：城市广场、大型公共场馆和明显地标优先，稳定商圈和大型 AOI 次之，小区/社区降级使用；地铁出入口统一归并为稳定的地铁站名，并低于大型地标；道路、小商铺、停车场、喷泉、基层组织机构以及场馆内部附属景点不得成为广场名称。
4. 同一批四广场尽量使用不同名称；缺少合格候选时保留中性编号，不编造名称，也不阻塞 `/geo/context`。
5. 地图请求必须发生在用户锚点事务之外，并以后台补全方式运行。本次 `/geo/context` 立即返回已有名称，命名完成后由后续静默刷新读取；高德超时、限流和返回异常都只影响命名，不得延长或破坏用户进入广场的主流程。
6. 多进程通过数据库原子认领中性广场并写入重试租约，同一广场同一时段只由一个进程请求地图。失败后短暂延迟，无合格候选时延长重试间隔，避免刷新页面造成外部 API 请求放大。
7. `AMAP_WEB_SERVICE_KEY` 只存在服务端受控环境；未配置 Key 时不认领、不请求，已有中性广场在未来配置 Key 后仍可自动补名。
8. 命名策略是可替换的领域端口。未来可加入运营人工名称、认证场馆名称或其他地图源，但来源优先级和修改审计必须明确，不把供应商响应结构渗透到广场核心模型。

## 影响

- 用户看到的广场名称可以从编号平滑升级为地标名称，聊天记录和未读状态不变。
- 地图故障不会造成定位失败或白屏。
- 数据库租约控制跨进程重复请求；未来水平扩容并出现大量新网格同时创建时，再在适配器边界增加全局 QPS 限流，不修改广场领域逻辑。
- 地标变化不会自动覆盖已经稳定命名的广场。未来如需改名，应通过带来源、版本和审计的独立重命名流程完成。

## 验收

1. 没有 Key 时 `/geo/context` 正常返回编号名称且不发外部请求；
2. 配置 Key 后，中性广场在下一次上下文刷新时获得稳定名称；
3. 四个广场不使用同一候选名称；
4. 高德超时或失败时接口仍成功，且不会在短时间内重复请求；
5. 改名前后 `plazaId`、`conversationId`、消息、未读和锚点保持不变；
6. 返回给客户端的数据不包含网格中心或用户精确坐标。
