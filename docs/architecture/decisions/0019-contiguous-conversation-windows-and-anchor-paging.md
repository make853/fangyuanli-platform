# ADR 0019：连续会话窗口与消息锚点分页

## 状态

已采纳。

## 背景

私聊和广场当前只加载最近消息。向上读取历史、首条未读和搜索结果都需要在不破坏当前阅读位置的前提下加载其他序号区间。若把相距很远的锚点页和最新页直接合并，中间未加载的消息会在界面上被误认为连续；若每个聊天页面分别维护分页，又会重新产生多套状态机。

## 决策

1. 私聊、广场、地点、活动和系统会话共用 `ConversationSyncController` 的 `beforeSequence`、`afterSequence` 与 `anchorSequence` 窗口。
2. 普通会话默认展示最新连续窗口；用户向上滚动时按最早已确认序号加载前一页，插入后保持原首条可见消息的屏幕位置。
3. 未读或搜索定位使用独立的连续锚点窗口，并明确保存 `hasEarlier`、`hasLater` 与锚点状态。禁止把锚点窗口和最新窗口跨缺口直接拼接。
4. 锚点期间到达的实时消息继续进入最新窗口和本地缓存，不直接追加到旧锚点窗口。用户向下加载至最新页或发送消息时恢复最新窗口。
5. 分页只由真实用户滚动触发；首次定位、布局变化、键盘开合和程序化跳转不得意外触发连续网络分页。
6. 服务端现有消息序号协议和数据库保持不变，不新增业务游标或场景专用消息接口。

## 影响

- 搜索、首条未读和未来回复/@定位获得同一数据边界。
- 地点和活动只需提供会话访问策略，不实现自己的历史加载。
- 锚点窗口与最新窗口分离会增加少量客户端状态，但避免了错误连续性和大批量消息一次性加载。

## 验证

1. 向上加载使用当前最早序号且不会重复请求；加载后原首条消息保持原屏幕位置。
2. 锚点页只显示连续上下文并正确返回 `hasEarlier`、`hasLater`。
3. 锚点期间实时消息不会跨缺口显示，向下回到最新窗口后只出现一次。
4. 键盘开合、首次底部定位和程序化滚动不会触发历史分页。
5. 私聊和广场复用同一时间线组件和控制器接口。

## 真机验收

待长聊天 staging 数据准备完成后，在 iPhone 真机验证向上加载不跳动、搜索定位、首条未读定位、实时新消息和返回最新消息。
