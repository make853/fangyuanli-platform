# 0009：版本化广场网格与持久锚点

- 状态：已接受
- 日期：2026-08-02

## 背景

广场一次展示一个主广场和三个相邻广场，四者均可查看和发言。GPS 漂移、网格边界和不同手机定位精度可能导致组合频繁变化。网格边长和投影还需要通过真实 iPhone 与高德地图验证，不能把第一版算法散落在控制器或客户端后永久锁死。

## 决策

1. App 只提交 GCJ-02 定位到 `POST /geo/context`，服务端返回不透明短期令牌和四个广场，不返回用户坐标。
2. 网格配置使用不可变 `plaza_grid_versions`。第一版以 500 米和 `gcj02-web-mercator-v1` 作为 staging 技术基线；真实地图验证不通过时创建新版本，不覆盖既有网格与广场 ID。
3. 投影、锚点决策、持久化和接口编排分层。替换投影或把锚点从 PostgreSQL 迁移到 Redis 时，不修改 OpenAPI 和移动端模型。
4. 广场按需懒创建，并在同一事务内创建 `plaza` 会话；事务级锁保证并发定位不会生成重复网格或孤儿会话。
5. 四格组合由主格、最近横向格、最近纵向格及其对角格组成。距离相等使用稳定格坐标排序，不随机交换。
6. 150 米内复用原组合。超过 150 米且组合变化时，默认要求定位误差不超过 80 米、连续三次命中新组合且停留至少 60 秒后才切换；所有阈值均为运行时配置。
7. 第一版锚点保存在 PostgreSQL，并按用户事务锁串行更新，服务重启不丢状态。达到高频定位规模后可在 Repository 边界内替换为 Redis，数据库保留关键快照。
8. 广场名称先使用稳定中性编号。高德地标命名属于后续适配器，名称变化不得改变广场 ID 或会话 ID。

## 影响与风险

- 第一版 Web Mercator 只用于稳定平面索引，不代表把 GCJ-02 当成 WGS84；其地面边长误差必须在上线前实机验证。
- 改变网格边长或投影会形成新网格版本，需要灰度和历史会话迁移策略。
- PostgreSQL 锚点适合 MVP 低频刷新；高并发时应迁移到 Redis，但不能让 Redis 成为广场 ID 的唯一持久来源。
- 服务端发言接口仍需再次校验短期位置令牌，不能只相信客户端显示出的 `canSpeak`。

## 验收标准

- 相同定位重复请求得到稳定的主广场与三个相邻广场。
- 150 米内漂移不切换；越界后未满足连续次数或停留时间时返回旧组合并标记重新计算中。
- 并发请求只创建一份网格和一份广场会话。
- 全局免打扰返回灰色未读，普通未读返回红色，响应中不包含用户经纬度。
- 服务重启后锚点继续生效；网格版本变化时建立新锚点而不复用旧组合。
