# 0006：移动端本地消息快照与序号增量同步

- 状态：已接受
- 日期：2026-08-02

## 背景

私聊最初只在 Riverpod 控制器中保留十分钟内存状态。离开页面后短期返回很流畅，但 App 进程结束或内存回收后仍要重新下载消息，无法提供稳定冷启动和离线历史。服务端已经为每个会话分配严格递增的 `sequence`，并支持 `afterSequence` 增量读取，因此客户端不应另造时间游标。

## 决策

1. 私聊消息复用唯一的 `AppDatabase`，通过数据库版本2迁移加入消息表；禁止会话模块单独打开数据库。
2. 所有记录以 `owner_user_id` 和 `conversation_id` 隔离。消息ID是幂等主键，会话内序号建立唯一约束和倒序索引。
3. SQLite保存完整消息JSON载荷，同时单独索引序号和创建时间。以后加入图片、语音、视频、回复和撤回时扩展消息载荷，不重新设计缓存表。
4. 打开聊天先读取最近本地快照完成稳定首屏，再以最后一条本地 `sequence` 调用 `afterSequence`；服务端单页最多100条，客户端按 `hasLater` 连续补拉并按消息ID合并、按序号排序。
5. 首次访问或本地快照损坏时退回服务器最新页。任一缓存消息无法解析时清除该会话快照并完整重取，不能带缺口继续增量同步。
6. HTTP发送成功和实时 `message.created` 到达后立即写入同一缓存。服务器仍是发送结果、权限和消息顺序的最终权威。
7. 本批次不实现离线待发送队列。断网发送仍明确失败，后续 outbox 必须保存稳定 `clientMessageId`、账号归属和发送状态，不能伪装成服务器已接收。
8. 图片和视频二进制继续由媒体缓存管理；消息数据库只保存媒体引用和展示载荷。普通媒体清理不得删除文字消息索引。

## 影响与风险

- App 冷启动或页面状态释放后仍可立即显示上次成功同步的聊天记录；网络恢复后只传输新增消息。
- A/B账号即使使用同一台手机也不会互读本地消息。
- 数据库版本迁移是非破坏性的，资料快照从版本1升级后保留。
- 本地数据库可能随使用时间增长。正式加入聊天媒体前需要补充按账号统计、用户主动清理和媒体/文字分级清理策略。
- 当前聊天页只展示最近本地窗口，向上加载更早记录和搜索锚点将在现有 `beforeSequence` / `anchorSequence` 协议上继续实现。
- 本决定最初通过好友私聊纵切验证；广场、地点、活动和系统会话必须复用同一底座，统一后的长期边界见 `0008-unified-conversation-cache-and-sync-engine.md`。

## 验收标准

- 已访问会话在 App 彻底退出后重新打开，先显示本地消息且不出现整页闪屏。
- 本地最后序号为 N 时，只请求 `afterSequence=N`，重复网络或实时消息不会显示两次。
- 连续缺失超过100条时按 `hasLater` 完成多页补拉并保持序号顺序。
- 本地数据库从版本1升级到版本2后资料快照仍在，A/B账号消息互相不可见。
- 缓存损坏或SQLite不可用时仍可从服务器进入聊天，不阻断发送和已读回执。
