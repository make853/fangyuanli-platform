# 0007：移动端账号概览快照

- 状态：已接受
- 日期：2026-08-02

## 背景

完整资料和私聊消息已经采用本地优先，但联系人与会话列表仍只存在页面内存中。真机飞行模式验收发现：已缓存的聊天记录可以立即显示，联系人 Bb 却会在联网冷启动时先消失，等待接口完成后才出现。这会让用户误以为好友被删除，也会导致会话入口和未读状态发生首屏跳变。

联系人、会话列表、地点列表和活动列表都属于“账号概览”，但它们的业务模型、更新频率和失效规则不同。不能为消除闪动而把所有列表塞进一个通用业务对象，也不能让每个模块自行创建数据库。

## 决策

1. 唯一的 `AppDatabase` 通过版本3迁移增加通用 `account_snapshots` 表，以 `(owner_user_id, snapshot_key)` 作为主键，并保存独立的载荷版本。
2. 通用存储只负责账号隔离、版本化JSON和损坏清理；好友与会话模块分别维护强类型快照适配器，禁止通用存储理解业务字段。
3. 联系人、好友申请、黑名单和会话概览采用 stale-while-revalidate：冷启动先显示本地快照，再静默请求服务器；网络成功后替换快照，失败时保留本地内容并记录错误。
4. 备注、动态权限、置顶、拉黑、解除拉黑、删除好友、未读数和会话本地投影在成功后立即写入快照，避免必须刷新页面才能看到结果。
5. 快照严格按当前登录账号隔离。切换账号不得读取上一账号内容；服务端仍是关系、权限、消息顺序和最终数据的权威来源。
6. 未来地点、活动等列表可复用通用存储，但必须新建自己的强类型适配器、快照键、载荷版本和自动化测试，不能依赖好友或会话结构。
7. 本地快照损坏、版本不兼容或SQLite不可用时删除对应快照并退回网络，不阻断登录和核心业务。

## 影响与风险

- 已经成功加载过的好友和会话会在后续冷启动立即出现，后台同步不再先清空列表。
- 第一次安装或从旧版本升级后仍需成功联网一次，才能生成首份好友与会话快照。
- 离线时可能短暂展示上次同步的关系和未读数；任何写操作和权限判断仍必须由服务端确认。
- JSON快照便于低耦合迭代，但不适合复杂查询。消息历史继续使用规范化消息表，后续若列表需要分页离线搜索，应新增专用表而不是无限扩大JSON。

## 验收标准

- 在线成功加载联系人和会话一次后，彻底退出 App 并在飞行模式重开，联系人与会话入口立即出现。
- 恢复网络后，旧快照保持显示，服务器结果静默更新，不出现空白、字母占位或整页闪动。
- 修改备注、置顶、拉黑、解除拉黑后，当前页面与下一次冷启动都显示最新成功状态。
- A/B 两个账号在同一设备上的好友、黑名单、会话和未读快照互不读取。
- 快照版本错误或内容损坏时可以自动退回服务器数据。
