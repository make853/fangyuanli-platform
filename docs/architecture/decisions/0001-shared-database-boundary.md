# ADR 0001：统一数据库连接与事务边界

- 状态：已接受
- 日期：2026-08-01
- 范围：NestJS API 模块化单体

## 背景

账号、关系、会话、资料和媒体模块最初各自创建一个 PostgreSQL 连接池，并在 Repository 内重复实现提交、回滚和关闭逻辑。该方式适合快速验证首条业务纵切，但继续增加地点、活动、动态和通知模块会线性增加连接数，并阻碍跨模块事务、可靠事件和统一数据库观测。

技术方案计划使用 Kysely 与 `pg`，而首批实现使用了参数化原生 SQL。直接一次性改写全部查询会放大回归范围，不符合当前的小步迁移原则。

## 决定

1. API 运行时通过全局 `DatabaseModule` 创建唯一共享连接池；
2. Repository 只依赖 `DatabaseService` 和稳定的 `QueryExecutor`，不得直接依赖 `pg.Pool` 生命周期；
3. `DatabaseService` 统一提供查询、提交、回滚和连接释放；
4. 使用异步事务上下文复用环境事务，使未来应用服务可以协调多个 Repository；
5. SQL migration 保持数据库结构的唯一事实来源；
6. Kysely 仅在该边界内按模块渐进引入，不要求一次性重写已有查询；
7. 迁移进程继续使用独立短连接和 advisory lock；
8. 跨事务的异步副作用后续通过事务发件箱实现，不把数据库事务无限延伸到 Redis、COS 或推送服务。

## 结果

正面影响：

- 新增模块不会再增加独立连接池；
- 数据库连接配置、关闭和事务行为只有一个实现；
- 未来可在不修改业务模块的情况下增加监控、慢查询记录、Kysely或测试替身；
- 跨模块用例可以共享事务，同时保持模块化单体边界。

需要承担：

- 共享连接池需要通过压测调整 `DATABASE_POOL_MAX`；
- 环境事务只能用于数据库操作，不能在事务中等待长时间网络请求；
- 事务回调必须等待全部数据库操作，禁止创建脱离回调生命周期的异步数据库任务；
- 嵌套调用加入同一事务，不提供隐式 savepoint；需要局部回滚时必须显式设计；
- 数据访问层仍需通过集成测试验证原生 SQL、锁和约束。

## 不采用的方案

- 每个 Repository 独立连接池：连接数随模块和实例数量增长，已经不适合继续扩展；
- 立即全面迁移 Kysely：变更范围过大，无法独立验证连接治理收益；
- 当前阶段拆分数据库或微服务：引入分布式事务和运维成本，超出 MVP 需要。
