# 0005：移动端本地优先资料快照

- 状态：已接受
- 日期：2026-08-02

## 背景

好友列表、私聊和个人资料依赖同一套用户身份。仅使用页面内存状态时，Provider 被释放或 App 重启后会重新等待网络，产生整页加载、头像占位闪烁和弱网不可用。单纯延长内存缓存时间不能解决冷启动，也不能承载后续本地聊天记录。

## 决策

1. Flutter 建立唯一的本地 SQLite 数据库边界，资料快照、后续聊天记录和同步游标通过版本迁移逐表加入，不允许各功能私自打开数据库。
2. 完整资料快照以 `(owner_user_id, target_user_id)` 作为主键，严格按当前登录账号隔离；服务端 PostgreSQL 仍是权限和数据的权威来源。
3. 页面采用 stale-while-revalidate：先读取本地快照完成稳定首屏，再静默请求服务器；成功后只替换变化的状态并更新快照。
4. 资料快照保留 `profileVersion`、关系裁剪结果和媒体 ID。旧版本网络响应不得覆盖较新的本地快照。
5. 头像与背景图片仍由媒体缓存以稳定 `mediaId` 作为键；资料数据库只保存媒体视图和短期读取地址，不复制图片二进制。
6. 本地数据库异常、损坏或不可用时必须退化为网络读取，不能阻断登录、资料修改或聊天。
7. 普通“清理媒体缓存”未来不得删除文字消息和资料索引；删除账号本地数据、清理聊天记录和退出登录是三个独立动作。

## 影响

- 缓存过的资料和聊天入口在 App 冷启动后也可立即展示，后台刷新不会清空整个页面。
- 资料修改成功后同时写入当前账号的快照，首页、资料页和后续共享数据层可以读取同一结果。
- 已经在终端展示过的数据可能在离线时继续可见；恢复联网后以服务端最新隐私裁剪收敛。这与本地优先离线体验一致。
- 下一阶段本地消息表必须复用同一数据库和账号隔离规则，并用服务端会话序号做增量同步、排序和幂等去重。

## 验收标准

- 第二次进入已访问资料以及 App 冷启动后进入资料，不出现全屏加载闪屏。
- 弱网或断网时仍显示最后一次成功取得的资料快照。
- 后台取得新版本后只更新头像、昵称、签名或背景墙等变化区域。
- A/B 两个账号在同一设备上的快照互不读取、互不覆盖。
