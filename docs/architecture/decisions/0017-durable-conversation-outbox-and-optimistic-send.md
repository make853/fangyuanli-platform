# 0017：统一会话持久化 Outbox 与乐观发送

- 状态：已接受
- 日期：2026-08-03

## 背景

真实广场聊天接入后，移动端仍在等待 HTTP 成功才把消息加入时间线，导致点击发送后出现等待圈。网络失败时消息不会留在原位置，也无法按原幂等键重试。该体验如果分别在私聊、广场、地点和活动修补，会产生多套失败状态与重复消息风险。

## 决策

1. 所有会话场景复用一套账号隔离的持久化 `conversation_outbox`，不得为某个页面另建发送队列。
2. 客户端点击发送时先生成稳定 `clientMessageId`，立即把 `sending` 消息加入本地时间线并清空输入框；网络请求在后台执行，不显示阻塞式转圈。
3. 服务器确认消息后，以相同 `clientMessageId` 将本地消息替换为带正式 `messageId` 和会话 `sequence` 的权威消息。实时事件与 HTTP 响应无论谁先到，都使用同一键去重。
4. 网络或权限失败时，本地消息保留在原位置并标记为 `failed`。气泡左侧显示红色感叹号；点击后复用原 `clientMessageId` 重试，禁止生成新键导致重复消息。
5. Outbox 与服务端历史缓存物理分离。待发送消息不得伪造服务器序号，也不得参与 `afterSequence`、已读游标或历史分页。
6. Outbox 按账号和会话持久化。App 重启后未确认的 `sending` 状态降级为可人工重试的 `failed`，避免误称仍在发送；未来媒体消息继续复用同一状态机，只扩展载荷与上传依赖。
7. 返回前台和重新进入会话时优先使用进程内同步快照完成首帧，再静默读取 SQLite 和服务端增量，避免空白帧后整页替换。
8. 长时间线首次进入时先完成底部定位再展示，禁止先绘制顶部消息后下一帧跳到底部。键盘开合只用无动画的底部锚点修正；同一 `clientMessageId` 的发送状态更新不是新消息，不得重复触发滚动。
9. 场景写权限中的短期凭证不得由页面自行拼接。统一会话发送器通过 `ConversationSendAccessResolver` 在实际投递前取得最新权限；广场位置令牌缺失、即将过期或被服务端判定过期时，只允许静默刷新一次，并用原 `clientMessageId` 重试，避免把可恢复的凭证失效误显示为发送失败。
10. 会话控制器的身份只由稳定的会话标识决定，位置令牌、角色票据等短期权限不得进入 provider scope 或页面 Key；权限刷新不能重建时间线、头像或输入框。

## 影响

- 文字消息从“网络成功后显示”改为“本地立即显示、后台确认”。
- 服务端现有幂等约束成为重试正确性的必要条件。
- SQLite 升级到 v5，新增 outbox 表，不破坏 v1-v4 的资料、概览和消息缓存。
- 地点和活动接入真实会话时自动获得同一发送失败与重试行为。
- 位置、角色、禁言等场景凭证继续由业务适配器提供，通用 outbox 不依赖任何具体场景字段。

## 验收

1. 正常网络下点击发送无等待圈，消息同帧出现在底部，确认后不跳动、不重复。
2. 断网发送保留消息并出现红色感叹号；恢复网络后点击感叹号只产生一条服务端消息。
3. App 重启后失败消息仍在原会话，其他账号不可见。
4. HTTP 响应与实时事件先后顺序互换时仍只显示一条。
5. 私聊、广场、地点和活动使用同一实现与测试契约。
6. 首次进入长聊天不闪现顶部消息；键盘收起后最后一条完整可见，页面不因确认同一条乐观消息而二次滚动。
7. 缓存广场可先显示但短期位置令牌已失效时，正常联网发送应静默刷新凭证并只产生一条消息，不出现红色感叹号。
8. 广场位置令牌刷新时，当前聊天、历史气泡、头像和输入框保持原位，不得因短期凭证变化重建页面。
