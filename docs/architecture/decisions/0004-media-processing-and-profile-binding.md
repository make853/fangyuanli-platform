# ADR 0004：媒体处理 Worker 与资料媒体绑定

- 状态：已接受
- 日期：2026-08-01
- 范围：图片处理、私有媒体读取、头像/背景墙绑定和旧媒体清理

## 背景

移动端已经能把图片压缩后直传私有 COS，服务端也能确认对象存在并创建
`processing` 状态的媒体记录。当前仍缺少四个闭环：把原始图片转换成稳定的展示规格、
把 `ready` 媒体安全绑定到用户资料、向有权限的查看者提供短期读取地址，以及在替换后
延迟清理旧对象。

这套能力未来还会被动态、聊天、活动和举报复用。若把图片处理直接塞进上传完成请求，
或由资料模块自行操作 COS，会形成长事务、重复权限规则和难以恢复的半完成状态。

## 决定

1. 上传确认只负责校验原始对象、创建 `media_assets` 和持久化处理任务；媒体保持
   `processing`，不在 HTTP 请求中执行图片解码、转码或 COS 复制；
2. 新增 PostgreSQL 持久化任务表 `media_processing_jobs`。每个媒体只有一个当前处理
   任务，记录状态、尝试次数、下次执行时间、租约、失败代码和更新时间；
3. Worker 与 API 使用同一代码库、同一媒体领域模块，但以独立进程和 systemd 服务
   运行。第一阶段在 `apps/api` 增加专用 Worker 入口，不复制 Repository 和业务模型；
   只有需要独立发布或大规模扩容时再提取为单独应用；
4. Worker 使用短事务和 `FOR UPDATE SKIP LOCKED` 领取任务。COS 下载、解码和上传均在
   事务外执行，完成后再用短事务更新结果；租约超时的任务可以被其他 Worker 重领；
5. 派生对象键必须确定性生成，例如
   `processed/{ownerUserId}/{mediaId}/avatar-512.webp`。重复执行覆盖同一目标，不产生
   新媒体 ID 或无界重复文件；
6. `media_assets.object_key` 继续表示私有原始对象，新增 `display_object_key` 表示主要
   展示图，现有 `thumbnail_object_key` 表示列表缩略图。数据库永远不保存带签名 URL；
7. 头像第一版生成 512×512 展示图和 128×128 缩略图；背景墙生成最长边不超过
   1920 的展示图和最长边不超过 480 的缩略图。输出统一自动旋转、移除 EXIF/GPS，
   并限制解码像素，防止异常图片耗尽内存；
8. 头像和背景墙在上传前由客户端转换为不带元数据的标准图片。头像裁剪属于客户端
   交互，Worker 只验证比例并生成规格，避免服务端猜测用户想保留的画面区域；
9. 处理成功后状态变为 `ready`；可恢复错误按指数退避重试，最多五次；确定性格式错误
   或超过像素上限时标记 `failed` 并返回稳定错误码；
10. `PATCH /me` 只有在同一数据库事务中确认媒体属于当前用户、用途匹配、类型为图片、
    状态为 `ready` 且未删除后，才允许写入 `avatar_media_id` 或
    `background_media_id`。资料版本冲突仍返回 409；
11. 新媒体绑定成功后取消其普通过期时间；被替换或主动移除的旧媒体进入至少 24 小时
    宽限期。清理任务在删除 COS 前必须再次确认没有资料或其他业务引用，并尊重
    `compliance_hold`；
12. 私有桶不改为公有。`MediaDeliveryService` 按业务权限生成不超过 10 分钟的单对象
    GET 签名 URL；头像可以随最小资料视图返回，背景墙只随完整资料视图返回；
13. CAM 权限按前缀和动作扩充：Worker 只读 `temporary/*`，读写删
    `processed/*`；客户端仍只能得到单对象 PUT 地址。不得把角色扩大为整桶全权限；
14. 原始对象和无引用媒体由独立清理任务处理。处理成功的资料原图保留短期恢复窗口后
    删除；处理失败、上传未确认和长期未绑定媒体均有明确到期规则。

## 数据与接口影响

- 新迁移增加 `media_assets.display_object_key`、处理完成/失败信息和
  `media_processing_jobs`；`user_profiles` 已有头像与背景媒体外键，无需重复字段；
- `ObjectStorageAdapter` 增加读取对象、写入派生对象和生成短期读取 URL 的端口；
- `MediaRepository` 增加任务领取、完成、失败、租约恢复和清理候选查询；
- `ProfileRepository` 返回内部媒体引用，`ProfileService` 通过媒体交付服务生成查看者
  有权获得的 `MediaView`；Repository 不拼 COS URL；
- Flutter 只在媒体变为 `ready` 后提交资料绑定，并保留上传、处理、绑定三个阶段各自的
  错误与重试反馈。

## 结果

正面影响：

- HTTP 上传接口保持快速，服务重启或 Worker 崩溃不会丢失处理任务；
- 头像、背景墙、动态和聊天可以复用上传、处理、读取和清理端口；
- 资料更新仍是单一事务，不会出现数据库指向尚未完成或属于他人的图片；
- 对象键、任务和资料版本都具有幂等边界，局部重试不会制造重复数据；
- 私有媒体权限留在服务端，COS 地址泄露窗口被限制在短时间内。

需要承担：

- staging 和 production 需要新增 Worker systemd 服务、健康监控和最小权限 CAM 动作；
- PostgreSQL 任务队列适合当前规模，但需要监控积压、失败率和最长处理耗时；
- Flutter 通过独立 `MediaImageCropper` 端口接入系统原生头像裁剪，上传协调器只负责
  选择、预处理、上传和等待状态；以后替换裁剪组件不会改动资料绑定或上传状态机；
- 自动化已覆盖裁剪取消不上传、背景墙不强制方形裁剪，以及 A/B 资料媒体权限；
  原生裁剪手势、相册/相机权限文案仍需在真机发布前做一次人工视觉验收；
- 以后视频转码负载明显增大时，Worker 可以独立扩容或迁移到专用队列，但业务状态机不变。

## 不采用的方案

- 在上传完成接口同步处理图片：请求时间长，失败时难以判断上传、处理和绑定分别到了哪一步；
- 由 Flutter 直接生成所有正式派生图：客户端版本和设备差异会导致规格不一致，且不能作为安全校验；
- 把 COS 桶改为公有读：无法执行资料权限、拉黑和举报证据隔离；
- 只在内存或 Redis 中保存处理任务：进程或服务重启可能丢任务；
- 立即删除被替换头像：多设备缓存、回滚和并发请求会出现短暂破图；
- 当前就拆成独立微服务：增加部署、契约和排障成本，但尚无独立扩缩容证据。
