# 0004：版本化用户身份摘要与稳定媒体缓存

- 状态：已接受
- 日期：2026-08-02

## 背景

头像、昵称会同时出现在好友申请、联系人、会话列表、聊天消息、动态、活动和地点群中。若每个页面临时读取完整个人资料，会产生 N+1 请求、重复状态和“字母占位先出现，随后闪成头像”的体验。头像签名地址只有短期有效，也不能直接作为长期缓存键。

## 决策

1. PostgreSQL 中的个人资料仍是权威数据；COS 保存媒体对象。
2. 高频列表接口返回轻量用户身份摘要：`userId`、展示名、头像媒体视图和 `profileVersion`，不附带签名、背景墙等完整资料。
3. 身份摘要由资料模块批量投影并签发媒体读取地址，好友与会话模块不得逐用户调用完整资料接口。
4. Flutter 使用 `mediaId` 作为稳定磁盘缓存键，不使用会变化的短期签名 URL 作为缓存身份。
5. 地址或资料刷新时继续展示已有图片；新图片准备完成后再替换。只有从未存在头像时才显示文字占位。
6. 资料修改成功后发布 `profile.updated`，事件只携带 `userId` 与 `profileVersion`。在线好友静默刷新身份摘要；离线设备在恢复前台时通过列表接口最终收敛。
7. 好友备注、置顶和权限属于有方向的关系数据，不写入公共身份摘要，也不被对方资料更新覆盖。

## 影响

- 好友列表、会话列表和聊天消息共享同一份头像身份语义。
- 增加动态、活动和地点群时应复用身份摘要，不得建立各自的用户资料缓存。
- 完整个人资料继续按隐私规则单独读取，避免高频列表过度取数或泄露字段。
- 头像媒体替换必须生成新的 `mediaId`；同一媒体 ID 不得原地覆盖内容。

## 后续

- 动态、活动、地点群接入真实用户数据时复用当前身份摘要服务。
- 达到多实例规模后，可在资料模块内部加入短期 Redis 投影缓存，但 API 和客户端模型保持不变。
